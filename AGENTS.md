# Repository Guidelines

## Language

**Spanish is the default for everything produced here, unless the user asks otherwise
in the request at hand.** This covers both sides of the work:

- **Replies to the user.** Answer in Spanish, whatever language the question was asked in.
- **Generated documents.** Every phase deliverable written into `.context/`, every prompt,
  guide, and note. Match the register of the documentation already in the repository.

Keep technical terms and code identifiers in their original form — do not translate a
field name, a status value, an endpoint, or a tool name. Write Spanish with full
orthographic correctness: accents and `ñ` always, never their ASCII substitutes.

One standing exception: **commit messages, branch names, and the agent instruction
files themselves (`AGENTS.md`, `CLAUDE.md`) follow the repository's existing English
history.** Everything else is Spanish.

## Project Structure & Module Organization

This repository holds the QA working context for the product, not the product itself: there is no application code, no build, and no `src/` or `tests/` directories. `.prompts/` stores the AI workflows for phases 1–7; `.documents/Fases/` explains the method behind each phase. `.guides/` covers Git, LLM clients, MCP servers, and Postman setup. `.context/` is the project knowledge base — everything the prompts read in order to work, whatever its origin: documentation that already existed, deliverables generated by a phase, or items pulled down from an external tool such as Jira. Root-level Markdown covers onboarding, scope, and pending work.

## `.context/Confluence-corporativo/` is historical record

That folder is a **manual backup of the corporate Confluence, which is no longer reachable**. It cannot be refreshed or re-exported. What was saved is all that remains.

The pages document the **start of the project**: the initial business and technical discussions — what was agreed, what was ruled out, and the reasoning behind both. That history is not written down anywhere else.

**Never edit these files.** They are a record, not working documentation. Editing one fixes nothing: it destroys the only account of what the team decided at the time, and leaves no way for the next reader to tell what was changed.

How to use them when analysing:

- **Treat them as valid evidence.** Where nothing more recent speaks to a question, what these documents say stands, and you can build on it.
- **Current evidence outranks them.** Observed behaviour in the running product, a recent ticket, or a newer document wins over a page here. In that case the page is *stale*, not wrong — it was true when it was written.
- **Discrepancies are findings, not errors to clean up.** When two documents disagree, or a question has no answer anywhere, record it in the phase deliverable, name the documents involved, and state which one you relied on and why.

## Skills

**New skills go in `.agents/skills/<name>/SKILL.md`** — that is the default, and it holds
unless the user asks for a different location in the request at hand. `.agents/` is the
portable spot: Codex, Copilot and other agents read it as it is, so a single file serves
every tool instead of one copy per vendor.

The directory must sit **exactly one level below `.agents/skills/`**. A bare
`skills/SKILL.md`, anything nested deeper, and a `skills/` directory outside the agent
folder are all silently ignored: the file is never read and nothing reports an error.
Unlike `CLAUDE.md`, which can import `AGENTS.md`, skills have no import mechanism, so the
real file has to sit where the runtime looks — there is no way to keep it elsewhere and
point at it.

**When working in Claude Code, apply
[`.guides/LLMs/claudeCode/claude-Code-skills-enlace.md`](.guides/LLMs/claudeCode/claude-Code-skills-enlace.md).**
Claude Code does not read `.agents/skills/`; it only looks in `.claude/skills/`. A skill
created under `.agents/` stays invisible to it — with no error — until it is linked. That
guide carries the link commands for Windows and macOS, and the loop that links every skill
at once. The links need no `.gitignore` upkeep: `.gitignore` already excludes everything
under `.claude/skills/` and re-includes only the skills that genuinely live there. Adding a
skill of Claude Code's own — one that is not a link — is what calls for a new `!` line.

**The location is tool-specific; the format is not.** `SKILL.md` with `name`, `description`,
and optional `allowed-tools` frontmatter is a portable specification. So write the body
tool-agnostic — no vendor names, no assumptions about which assistant is reading it — and a
skill copied into another tool's directory keeps working.

Two rules for the content:

- **The `description` is the trigger.** It is matched against the user's request to decide
  whether the skill loads, so it must say *when to use this*, in the words a user would
  actually type — not just what it does.
- **Read conventions, do not hardcode them.** A skill that encodes this repository's commit
  style stops being useful the moment the repository it runs in has a different one. Have it
  read `AGENTS.md` and the existing history instead.

## Development and Validation Commands

No build tool or automated test runner is configured. Use repository-level checks instead:

```powershell
git status --short                  # Review changed and untracked files
git diff --check                    # Detect whitespace errors
git diff --stat main...HEAD         # Summarize the proposed contribution
rg --files --hidden -g '!.git/**'   # Inventory repository content
```

Preview changed Markdown in an editor and follow every relative link. For command examples, run them in the documented shell when practical and state any unverified prerequisites.

## Writing Style & Naming Conventions

Write project documentation in Spanish (see **Language** above), using UTF-8, ATX headings, short paragraphs, and fenced code blocks with a language tag. Preserve the repository's normalized text handling from `.gitattributes`. Keep numbered phase directories aligned across `.prompts/` and `.documents/Fases/`. Name new prompt files with descriptive kebab-case, such as `test-plan-generator.md`. Prompts should clearly identify their role, prerequisites, required output, and next step. Configuration examples must use `.template.json` or `.template.toml` and placeholder values.

## Testing Guidelines

For documentation changes, verify rendered headings, tables, code fences, paths, and links. For prompt changes, execute the affected flow when possible and confirm prerequisite checks, output format, phase chaining, and the intended `.context/` destination. Record what was actually validated; do not imply successful Jira, MCP, API, or browser execution without evidence.

## Commit & Pull Request Guidelines

Never work directly on `main`. Use branches such as `docs/US-1122-login`, `prompts/mejora-analisis`, `test/regresion-pagos`, or `fix/typo-readme`. Follow the history's Conventional Commit style: `docs(context): ...`, `feat(prompts): ...`, or `chore(repo): ...`. Pull requests should explain the purpose, list affected phases or paths, link the relevant issue/Jira item when available, and describe validation. Include screenshots only when rendered or visual output changed.

## Security & Configuration

Never commit tokens, credentials, `.env` files, private keys, or Postman environments. Keep only sanitized templates, and review material imported into `.context/` before committing it. Local MCP configs are allowed, provided you never commit files containing real credentials.

### Where credentials live

Two mechanisms, and a secret belongs to exactly one of them:

- **A credential consumed by an MCP server** (Jira, Postgres, Playwright, Postman) belongs to that server's configuration, which can be global in the user's home directory or local in the project. If local, the configuration file containing real credentials must never be committed. The agent never handles the value — it just calls the tool.
- **A credential the agent uses to call an API directly** (`curl`, `fetch`) belongs in `.env` at the repository root. Today that is Xray, which has no official MCP, plus the API and test-user credentials of phase 6.

`.env.example` is committed and lists **which** variables are needed, never their values; `.env` itself is ignored. When a prompt needs a credential that is not in `.env.example`, add the variable there — do not invent a second place to keep secrets.

### Never read a secret into context

Do not open `.env` to read a value, and never ask the user to paste one into the conversation. Either puts the secret in the session transcript, which is exactly what these files exist to prevent.

Load it in the shell and reference the variable instead, so the value is resolved by the shell and never enters the conversation:

```bash
set -a; . ./.env; set +a
curl -H "Authorization: Bearer $XRAY_TOKEN" ...
```

For the same reason, never run `echo $VARIABLE` or `curl -v` on an authenticated request: both print the secret into tool output, which *is* in context.

If a required variable is missing, say which variable is missing by name and stop. Never guess a value, and never work around the gap by asking for the secret directly.
